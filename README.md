# tugmcp (Tugboat MCP)

**English** | [简体中文](README.zh-CN.md)

`tugmcp` is a **standalone, reusable, GUI-free C++17 MCP library**. It provides both an MCP server and client, supports stdio and Streamable HTTP, and targets **2026-07-28** with **2025-11-25** fallback.

The name “tugboat” reflects its role: the library does not implement business logic. It tows a host application’s MCP capabilities onto stdio/HTTP and keeps protocol, transport, schema, concurrency, and packaging concerns inside one reusable component.

## Status

**M1–M6 are complete** (core+stdio, schema/canonical/conformance, 2026 server/client, 2025 server/session, 2025 client/replay, host-adapter hooks, legacy HTTP+SSE). The default build artifact is a static library; **single-header release artifacts** `tugmcp.hpp` / `tugmcp_http.hpp` / `tugmcp_http_tls.hpp` are also available (generation, packaging, SHA256, licenses, and external verification included). The split-header `TUGMCP_HEADER_ONLY` mode is still unimplemented (configure fails with `FATAL_ERROR`); the single-header artifacts do not depend on it. See [`docs/amalgamation.md`](./docs/amalgamation.md).

The default build is a static library; release-only single headers are generated by `tools/amalgamate.py` (`tugmcp.hpp`, `tugmcp_http.hpp`, `tugmcp_http_tls.hpp`). The split-header `TUGMCP_HEADER_ONLY=ON` mode is not implemented (FATAL); single-header consumption does not use that switch.

## What this library does not do

- Device control, business execution, parameter tuning, task semantics, hardware interlocks;
- GUI/UI framework integration;
- OAuth/OIDC authorization servers;
- REST/OpenAPI gateways;
- Device-safety conclusions.

These belong to the host application or hardware layer. The library provides protocol, transports, codecs, schema validation, cancellation/progress, and auth/approval/audit hooks.

## Quick start

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure --parallel 4
```

Single-header release:

```bash
cmake --build build --target amalgamate          # generate the three headers
cmake --build build --target amalgamate-release  # package into build/amalgamation/release
```

Implementation history and milestones are described in `designs/mcp-library-design.md` §22.1 and [`docs/roadmap.md`](./docs/roadmap.md): `M1 core+stdio` → `M1.5 schema/canonical+conformance` → `M2 2026 server+client` → `M3 2025 server/session` → `M4 2025 client/replay` → `M5 host integration` → `M6 legacy`.

## Build switches

| Switch | Default | Description |
|---|---|---|
| `TUGMCP_TLS` | OFF | Enable TLS |
| `TUGMCP_TLS_BACKEND` | `openssl` | TLS backend (currently OpenSSL ≥ 3.0 only) |
| `TUGMCP_USE_SYSTEM_DEPS` | OFF | **Unimplemented**: `ON` fails at configure; dependencies remain vendored |
| `TUGMCP_VERIFY_3RD_HASHES` | ON | Verify SHA256 of `3rd/` dependencies |
| `TUGMCP_WITH_HTTP` | ON | Build `tugmcp::http` |
| `TUGMCP_WITH_JSONCONS` | OFF | Build `tugmcp::schema_jsoncons` |
| `TUGMCP_WITH_VALIJSON` | OFF | Build `tugmcp::schema_valijson` |
| `TUGMCP_ENABLE_LEGACY_SSE` | OFF | Build the legacy HTTP+SSE adapter |
| `TUGMCP_BUILD_TESTS` | ON | Build test targets |
| `TUGMCP_HEADER_ONLY` | OFF | **Unimplemented**: split-header INTERFACE mode; `ON` is FATAL. Single-header artifacts do not use it |
| `TUGMCP_BUILD_EXAMPLES` | ON | Build `examples/` (`tugmcp_echo_server`, etc.) |
| `TUGMCP_BUILD_QT_EXAMPLE` | OFF | Build the Qt 5 Widgets example (`examples/qt_widgets_server`); requires `TUGMCP_WITH_HTTP=ON` and Qt5 Widgets (`CMAKE_PREFIX_PATH`) |
| `TUGMCP_CONFORMANCE` | OFF | Run the external conformance suite (requires Python3, npx/Node, HTTP and tests; builds `tugmcp_conformance_server`) |
| `TUGMCP_REQUIRE_EXTERNAL_AMALGAMATION` | ON | Keep single-header Inspector/conformance tests registered and fail loudly when tools are missing; `OFF` skips them |
| `TUGMCP_AMALGAMATION_RELEASE_DIR` | `${CMAKE_BINARY_DIR}/amalgamation/release` | Output directory for `amalgamate-release` |

TLS is off by default. Enabling it requires OpenSSL ≥ 3.0 (cpp-httplib) and `crypt32` on Windows, and only one OpenSSL may be used per process.

Dependencies come from `3rd/`. `TUGMCP_USE_SYSTEM_DEPS` is **not implemented**: `ON` fails at configure, and there is no automatic fallback to vendored sources.
